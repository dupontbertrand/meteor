# Meteor Server ESM Bundle — Prototype Specification

**Date:** 2026-03-30
**Author:** dupontbertrand (with Claude analysis)
**Status:** Prototype specification

---

## Objective

`meteor build --format=esm` produces an `index.mjs` with static ESM imports instead of `main.js -> runtime.js -> boot.js`.

**The question the spike must answer:** Can the Meteor bundler emit real ESM modules that boot without vm, without Reify, without program.json?

---

## Strict scope

### What we change

The server output format of `meteor build` — only when `--format=esm` is passed.

| Before | After |
|---|---|
| `main.js` (6 lines CJS) | `index.mjs` (static ESM imports) |
| `runtime.js` (Module.prototype patching + Reify) | **Removed** — native ESM |
| `boot.js` (vm.runInThisContext loop) | **Removed** — the imports ARE the loading |
| `program.json` (loading manifest) | **Removed** — the order is in the imports |
| `source-map-support` (monkey-patch) | **Removed** — native runtime source maps |
| `npm-require.js` (custom resolution) | **Removed** — standard resolution via import/require |

### What we DO NOT change

- `http.createServer` + Express -> unchanged
- DDP transport (SockJS or ws via PR #14231) -> unchanged
- MongoDB / Minimongo -> unchanged
- Accounts -> unchanged
- Tracker / reactive-var / reactive-dict -> unchanged
- Legacy format (`meteor build` without `--format=esm`) -> unchanged, all tests pass
- CLI / `meteor run` -> unchanged (stays on Node)
- Isobuild / build plugins -> unchanged (we only modify the output, not the pipeline)

## Target output format

### Entrypoint: `index.mjs`

```js
// Generated by meteor build --format=esm
// No runtime.js, no boot.js, no program.json

// 1. Configuration
import { config } from './__meteor_config.mjs';
globalThis.__meteor_runtime_config__ = config;

// 2. Async context
import { AsyncLocalStorage } from 'node:async_hooks';
globalThis.__METEOR_ASYNC_LOCAL_STORAGE = new AsyncLocalStorage();

// 3. Meteor packages — static imports in dependency order
// (The bundler computes the order, emits the imports)
import './packages/meteor.mjs';
import './packages/random.mjs';
import './packages/ddp-common.mjs';
import './packages/ddp-server.mjs';
import './packages/mongo.mjs';
import './packages/accounts-base.mjs';
import './packages/accounts-password.mjs';
import './packages/webapp.mjs';

// 4. Application code
import './app/server/main.mjs';

// 5. Startup
import { _runStartupHooks } from './packages/meteor.mjs';
await _runStartupHooks();
```

### Each package: an ESM module

```js
// packages/meteor.mjs (generated by the bundler)
const startupHooks = [];

export const Meteor = {
  isServer: true,
  startup(fn) { startupHooks.push(fn); },
  // ... rest of the Meteor API
};

export async function _runStartupHooks() {
  for (const fn of startupHooks) await fn();
}

// Temporary backward compatibility
globalThis.Package = globalThis.Package || {};
globalThis.Package.meteor = { Meteor };
```

---

## Temporary compatibility

These mechanisms are maintained in the prototype to avoid breaking existing code:

| Mechanism | Why keep it temporarily | How |
|---|---|---|
| `globalThis.Package.xxx` | Existing code accesses exports via `Package.meteor.Meteor` | Each ESM package registers its exports in `globalThis.Package` |
| `Npm.require()` | Some packages use `Npm.require('lodash')` | Trivial facade: `export function NpmRequire(id) { return require(id); }` or `await import(id)` |
| `__meteor_runtime_config__` | All of Meteor depends on this global | Imported from `__meteor_config.mjs` then set as global |

## Key file to modify

**`tools/isobuild/bundler.js`** — the function that generates the content of `main.js` and the `programs/server/` structure.

Relevant lines:
- `_mainJsContents` (lines 208-214) — main.js template
- `programs/server/` output structure (around lines 3100-3150)

The change: when `--format=esm` is passed, instead of generating `main.js` + `program.json` + copying `boot.js`/`runtime.js`, emit:
- `index.mjs` with static imports in dependency order (this order is **already computed** by isobuild in `serverJson.load`)
- `packages/*.mjs` — each entry from `serverJson.load` becomes an ESM module
- `__meteor_config.mjs` — the config extracted from `config.json`
- `.map` files for source maps

## Steps

1. Read `bundler.js` to understand how `_mainJsContents` and the `programs/server/` structure are generated
2. Add a `--format=esm` flag (or detection in bundler options)
3. When ESM: generate `index.mjs` + `packages/*.mjs` instead of `main.js` + `boot.js` + `runtime.js` + `program.json`
4. Build a `--bare` app with `webapp`: `meteor create --bare spike-app && meteor add webapp`
5. `meteor build --format=esm ../spike-output --directory`
6. `cd ../spike-output/bundle && npm install`
7. Node test: `node index.mjs` -> the HTTP server responds to `curl http://localhost:3000/`
8. Bun test: `bun index.mjs` -> same test

## GO / NO-GO criteria

**GO:** `node index.mjs` boots the app and HTTP responds. Meteor packages initialize in the correct order. Startup hooks execute.

**NO-GO:** The bundler cannot emit packages as separate ESM modules (circular dependencies, unresolvable side effects, code that depends on dynamic evaluation via vm).

**If NO-GO:** Document exactly what blocks. The blocker will likely be in the way certain packages access exports from other packages (via `Package.xxx` instead of explicit imports). This would be the most valuable information from the spike.
