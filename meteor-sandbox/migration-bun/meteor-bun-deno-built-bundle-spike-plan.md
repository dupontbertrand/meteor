## 2. Built Bundle Execution Path

When you run `node main.js` on a built Meteor bundle, this is the exact call chain:

```
main.js (6 lines, generated by bundler.js:208-214)
  │
  ├─ process.argv.splice(2, 0, 'program.json')
  ├─ process.chdir(require('path').join(__dirname, 'programs', 'server'))
  ├─ require("./programs/server/runtime.js")({ cachePath: ... })
  │    │
  │    ├─ Patches Module.prototype.resolve      → Module._resolveFilename()
  │    ├─ Patches Module.prototype.load          → adds runSetters()
  │    ├─ Patches Module.prototype._compile      → reify transform
  │    ├─ Patches Module._extensions['.js']       → reify cache layer
  │    ├─ Adds Module.prototype.dynamicImport    → Promise.resolve().then(() => require(id))
  │    └─ Requires @meteorjs/reify (acorn + babel parsers, compiler)
  │
  └─ require('./programs/server/boot.js')
       │
       ├─ Requires: fs, path, source-map-support, semver, vm, async_hooks
       ├─ Reads: server-json.js → parses program.json via fs.readFileSync
       ├─ Reads: config.json, star.json via fs.readFileSync
       ├─ Installs source-map-support with custom retrieveSourceMap
       ├─ Sets up __meteor_bootstrap__ and __meteor_runtime_config__ globals
       ├─ For EACH file in serverJson.load:
       │    ├─ Reads file via fs.readFileSync
       │    ├─ Wraps in: (function(Npm,Assets[,specialArgs]){ <code> })
       │    ├─ Executes via: require('vm').runInThisContext(wrapped, {filename})  ← KEY
       │    └─ Calls result function with: [Npm, Assets, ...specialArgs]
       │
       ├─ Awaits debugger if METEOR_INSPECT_BRK
       ├─ Calls Meteor.startup hooks
       ├─ Calls main()
       ├─ If not DAEMON: process.exit(exitCode)
       └─ If METEOR_PARENT_PID: starts parent liveness check (process.kill(pid, 0))
```

**Helper files loaded by boot.js:**
- `server-json.js` — reads program.json from disk (fs, path, process.argv)
- `boot-utils.js` — pid validation (pure JS, no Node deps)
- `mini-files.ts` (compiled to JS) — path manipulation (path, os, process.platform)
- `npm-require.js` — Npm.require() resolution (assert, fs, path, underscore, require.resolve)
- `debug.ts` (compiled to JS) — just a `debugger` statement

**npm-rebuild.js** runs separately during `npm install` (postinstall script), NOT during server boot. It shells out to `npm rebuild` via `child_process.spawn`. Not relevant to runtime boot.

## 4. Top 5 Blockers for Built Bundles

### 1. Module.prototype patching in runtime.js — CROSS-RUNTIME
- **Files:** `runtime.js:24-96`
- **Reason:** Overrides `Module._resolveFilename`, `Module.prototype.load`, `Module.prototype._compile`, `Module._extensions['.js']`. This is how every `.js` file in the bundle gets reify-transformed at load time. In Bun, `Module._extensions` and `_cache` are documented as **no-ops**. If `_extensions['.js']` is a no-op, the entire reify cache layer is silently skipped — which might be OK (files still get compiled via `_compile` override) or might break entirely if `_compile` is also a no-op.
- **Type:** Meteor code issue (fixable by replacing Module patching with a different mechanism)
- **Can I work around it?** Yes — for a spike, you can try running without the cache layer. For a real fix, runtime.js would need to use `--require` or a loader hook.
- **Blocks:** "boots once" — this runs before any package code loads

### 2. vm.runInThisContext in boot.js — CROSS-RUNTIME (lower risk than expected)
- **Files:** `boot.js:414`
- **Reason:** Every server package is loaded via `vm.runInThisContext(wrappedCode, {filename})`. Both Bun and Deno document `vm.runInThisContext` as supported. The specific pattern (wrapping code in a function expression, executing it, calling the result) is standard. The risk is in edge cases: does the `filename` option work for stack traces? Does `displayErrors` work? Are there memory or performance issues?
- **Type:** Cross-runtime — likely works, but Bun's vm is described as "fragile"
- **Can I work around it?** Yes — replace with `new Function()` (loses filename), or `(0,eval)()`. Both are 1-line changes.
- **Blocks:** "boots once"

### 3. source-map-support / Error.prepareStackTrace — BUN-SPECIFIC
- **Files:** `boot.js:3,140-168`
- **Reason:** `source-map-support` relies on V8's `Error.prepareStackTrace` API to intercept stack trace generation. Bun uses JavaScriptCore, which does NOT have this API. Source maps will silently not work — errors will show compiled line numbers, not source line numbers.
- **Type:** Bun runtime issue (JSC vs V8)
- **Can I work around it?** For a spike: yes, just accept broken source maps. For production: would need a different source map approach on Bun.
- **Blocks:** "real production use" (not boot, not smoke test)

### 4. MongoDB driver memory leaks — BUN-SPECIFIC
- **Files:** Not Meteor code — it's in the `mongodb` npm package running on Bun
- **Reason:** 3 open issues spanning 18+ months (oven-sh/bun#12117, #24118, #25948). Memory grows unbounded with the official MongoDB driver on Bun. This is not a Meteor issue.
- **Type:** Bun runtime issue (external)
- **Can I work around it?** No. Must be fixed by the Bun team.
- **Blocks:** "real production use" (smoke tests may work fine for short-lived runs)

### 5. cluster import on Deno — DENO-SPECIFIC (lower risk than expected)
- **Files:** `webapp_server.js:20`, used at lines 1427-1429
- **Reason:** `import cluster from 'cluster'` at module level. On Deno, all cluster exports are stubs. However: `cluster.isWorker` returns `false` on Deno (stub), which means the cluster-specific code path at line 1427 is **never entered**. The import itself should not throw — it's just a module with stub exports.
- **Type:** Deno runtime issue, but actually benign for non-cluster deployments
- **Can I work around it?** Probably not needed — the stub returning `false` is the correct behavior for single-process.
- **Blocks:** Nothing for single-process. Blocks multi-process production deployment.

## 5. What is NOT a Blocker for This Scope

| Concern from first report | Why it doesn't matter here |
|---|---|
| **Dev bundle generation** | Built bundles don't use the dev bundle. They have their own `node_modules`. |
| **npm CLI semantics / shrinkwrap** | `npm install` in the bundle dir happens BEFORE switching runtimes. You run `npm install` with Node/npm, then `bun main.js`. |
| **npm-rebuild.js / node-gyp** | Runs as a postinstall script during `npm install`, not during server boot. Build with Node, run with Bun/Deno. |
| **CLI bootstrap / V8 flags** | The CLI stays on Node. Only the production server switches runtime. |
| **Isobuild vm.runInThisContext** | Build plugins run during `meteor build` (on Node). The built bundle has a separate, simpler vm usage. |
| **File watching (fs.watchFile)** | No file watching in production bundles. |
| **process.execPath for spawning** | Only used in `meteor run` dev mode, not in built bundles. |
| **Inspector protocol mismatch** | Debugging story matters for production, but doesn't block booting or smoke testing. |
| **CJS everywhere** | Built bundles are CJS — Bun handles CJS natively. Deno needs `--unstable-detect-cjs` but that's a flag, not a code change. |
| **Release/install/update** | Irrelevant — we're running an already-built bundle. |
| **Test infrastructure** | Out of scope — we're testing the runtime, not the test framework. |

## 6. Minimal Spike Plan

### Spike 0: Baseline — Verify runtime module support (30 min)

**Purpose:** Quick pre-flight check of the 4 critical Node APIs used by boot.
**Target:** Bun and Deno.
**Setup:** None — just shell commands.

```bash
# Bun
bun -e "console.log('process.version:', process.version)"
bun -e "const vm = require('vm'); const fn = vm.runInThisContext('(function(a,b){ return a+b })'); console.log(fn(1,2))"
bun -e "const vm = require('vm'); const fn = vm.runInThisContext('(function(Npm,Assets){ return {Npm,Assets} })', {filename:'test.js'}); console.log(fn({},{}))"
bun -e "const M = require('module'); const m = new M(); M.prototype.resolve = function(id){ return M._resolveFilename(id, this) }; console.log(typeof M._resolveFilename)"
bun -e "const M = require('module'); console.log('_extensions:', typeof M._extensions, '_compile:', typeof M.prototype._compile)"

# Deno
deno eval --unstable-detect-cjs --unstable-bare-node-builtins "const vm = require('vm'); const fn = vm.runInThisContext('(function(a,b){ return a+b })'); console.log(fn(1,2))"
deno eval --unstable-detect-cjs --unstable-bare-node-builtins "const M = require('module'); console.log('_resolveFilename:', typeof M._resolveFilename, '_extensions:', typeof M._extensions)"
```

**Expected failure modes:**
- Bun: `Module._resolveFilename` might be undefined or a no-op
- Deno: May need `--allow-read` or other permissions

**What it proves:**
- Success: the 4 critical APIs exist and do something → proceed to Spike 1
- Failure: identifies exactly which API is missing → refactor plan needed before any further spike

### Spike 4: Replace vm.runInThisContext with Function() in boot.js (2-4 hours)

**Purpose:** Remove the #2 blocker by proving boot.js can work without `vm`.
**Target:** Node first (prove it doesn't break), then Bun and Deno.
**Setup:** Patch the built bundle's boot.js.

In the built bundle's `programs/server/boot.js`, change line 414 from:
```javascript
const func = require('vm').runInThisContext(wrapped, {
  filename: scriptPath,
  displayErrors: true
});
```
To:
```javascript
const func = new Function('return ' + wrapped)();
```

Or, to preserve filename for stack traces (Node-specific but graceful fallback):
```javascript
let func;
try {
  func = require('vm').runInThisContext(wrapped, {
    filename: scriptPath,
    displayErrors: true
  });
} catch(e) {
  // Fallback for runtimes with incomplete vm support
  func = (0, eval)(wrapped);
}
```

```bash
# Test on Node first — must not break
node main.js
# Then test on Bun/Deno
bun main.js
deno run --allow-all --unstable-detect-cjs --unstable-bare-node-builtins main.js
```

**Expected failure modes:**
- `new Function('return ' + wrapped)()`: might fail if wrapped code uses strict-mode-incompatible syntax
- `(0,eval)(wrapped)`: works but no filename in stack traces
- Stack traces lose source file information (acceptable for spike)

**What it proves:**
- Success on Node: safe to PR as a runtime-agnostic fallback
- Success on Bun/Deno after this change: vm was the only boot-level blocker
- Failure: something else in boot.js is also broken

### Spike 5: MongoDB driver stability test (2-3 hours)

**Purpose:** Quantify the Bun MongoDB memory leak for Meteor-like workloads. Compare with Deno.
**Target:** Bun and Deno.
**Setup:**

Create `mongo-stress.js`:
```javascript
const { MongoClient } = require('mongodb');
const url = process.env.MONGO_URL || 'mongodb://localhost:27017/spike-mongo-test';

async function main() {
  const client = new MongoClient(url);
  await client.connect();
  const db = client.db();
  const col = db.collection('stress_test');

  const startRSS = process.memoryUsage().rss;
  console.log(`Start RSS: ${(startRSS / 1024 / 1024).toFixed(1)} MB`);

  for (let i = 0; i < 10000; i++) {
    await col.insertOne({ i, ts: new Date(), data: 'x'.repeat(100) });
    if (i % 100 === 0) {
      await col.find({ i: { $gt: i - 50 } }).toArray();
      const rss = process.memoryUsage().rss;
      console.log(`i=${i} RSS: ${(rss / 1024 / 1024).toFixed(1)} MB (+${((rss - startRSS) / 1024 / 1024).toFixed(1)} MB)`);
    }
  }

  await col.drop();
  await client.close();

  const endRSS = process.memoryUsage().rss;
  console.log(`End RSS: ${(endRSS / 1024 / 1024).toFixed(1)} MB (delta: +${((endRSS - startRSS) / 1024 / 1024).toFixed(1)} MB)`);
}

main().catch(e => { console.error(e); process.exit(1); });
```

```bash
npm install mongodb
# Node baseline
node mongo-stress.js
# Bun
bun mongo-stress.js
# Deno
deno run --allow-all --unstable-detect-cjs --unstable-bare-node-builtins mongo-stress.js
```

**Expected failure modes:**
- Bun: RSS grows monotonically, 5-10x of Node's RSS at 10k iterations
- Deno: RSS may be comparable to Node, or may show Atlas-specific issues

**What it proves:**
- Bun RSS < 2x Node: leak may be pattern-dependent, Meteor might be OK
- Bun RSS > 5x Node: confirms production blocker

## 7. Minimal Refactor Candidates

### R1: Make vm.runInThisContext in boot.js optional
- **File:** `tools/static-assets/server/boot.js:414-417`
- **Change:** Try `vm.runInThisContext` first, fall back to `new Function('return ' + wrapped)()`. Or: replace entirely with `new Function(paramNames, code)` which also supports a `sourceURL` pragma for stack traces.
- **Risk:** Low — `new Function()` is standard JS. Stack trace filename changes need testing.
- **Useful even without alternative runtime:** Yes — removes a Node-specific API from the hot path, simplifies the boot code.

### R2: Guard Module.prototype patching in runtime.js
- **File:** `tools/static-assets/server/runtime.js:24-96`
- **Change:** Check whether `Module._resolveFilename` and `Module._extensions` exist and are functional before patching. If not, skip the cache layer and fall back to inline reify compilation.
- **Risk:** Medium — could change module loading behavior if guards trigger incorrectly on Node.
- **Useful even without alternative runtime:** Yes — makes runtime.js more defensive, easier to debug.

### R3: Make cluster import conditional in webapp
- **File:** `packages/webapp/webapp_server.js:20,1427-1429`
- **Change:** Replace `import cluster from 'cluster'` with a lazy require inside the `if (unixSocketPath)` block where it's actually used.
- **Risk:** Very low — cluster is only used for worker naming with Unix sockets.
- **Useful even without alternative runtime:** Yes — reduces unnecessary imports, cleaner module graph.

### R4: Add `//# sourceURL=` pragma to vm-evaluated code
- **File:** `tools/static-assets/server/boot.js:399-400`
- **Change:** Append `\n//# sourceURL=${scriptPath}` to the wrapped code before execution. This gives `new Function()` and `eval()` a filename for stack traces, making the `vm` dependency less necessary.
- **Risk:** None — this is a standard browser/V8/JSC pragma.
- **Useful even without alternative runtime:** Yes — improves source attribution even in Node.

### R5: Remove hard semver version gate
- **File:** `tools/static-assets/server/boot.js:11-19`
- **Change:** Either make this configurable (`METEOR_SKIP_VERSION_CHECK=1`) or check for minimum feature support instead of Node version string.
- **Risk:** Very low.
- **Useful even without alternative runtime:** Marginally — helps users running newer Node versions before Meteor officially supports them.

## 8. Comparative Recommendation

### Fair Comparison

| Criterion | Bun | Deno |
|---|---|---|
| CJS support | Native, no flags needed | Requires `--unstable-detect-cjs` |
| vm.runInThisContext | Documented as working, "fragile" | Documented as working |
| Module._resolveFilename | Documented but unreliable | Documented, likely works |
| Module._extensions | **No-op** (documented) | Status unclear |
| HTTP server (node:http) | FULL | PARTIAL (sufficient for server) |
| cluster module | PARTIAL (isWorker works) | ALL STUBS (isWorker=false, fine for single-process) |
| MongoDB driver | **MEMORY LEAKS** (external, unresolved) | Atlas regressions (may be resolved) |
| Source maps (Error.prepareStackTrace) | **Not available** (JSC, not V8) | Available (V8 engine) |
| Native addons (N-API) | Supported, confirmed for bcrypt | Supported with `--allow-ffi` |
| Debugging | WebKit protocol (different toolchain) | V8/Chrome DevTools (same as Node) |
| Operational friction | Low (drop-in `bun main.js`) | Medium (needs 3-4 unstable flags) |

### Verdicts

**Is Bun worth a weekend spike?**
**Yes.** Bun is the fastest path to "does it boot?" The CJS-native support means zero flags needed. The main risk is runtime.js Module patching being a no-op, but that's exactly what the spike will reveal. Even if MongoDB leaks block production use today, proving the boot path works is valuable signal.

**Is Deno worth a weekend spike?**
**Yes, but as a parallel second experiment, not the primary.** Deno's V8 engine means better source-map and debugging compatibility long-term. But the flag burden (`--unstable-detect-cjs --unstable-bare-node-builtins --unstable-node-globals`) and the "unstable" label make it a harder sell to Meteor users. Worth testing alongside Bun to collect fair comparison data.

**Is Bun worth a 2-4 week contributor effort?**
**Only if Spike 1 succeeds AND the MongoDB leak is resolved or shown to be pattern-dependent.** If the spike reveals that runtime.js patching silently fails, the 2-4 weeks would be spent on runtime.js refactoring — which is valuable regardless but is not "Bun support."

**Is Deno worth a 2-4 week contributor effort?**
**Not today.** The unstable flags, the cluster stubs, and the operational friction make Deno a harder sell for the Meteor community. If Deno stabilizes its Node compat flags (removes "unstable" label), reconsider.

**What would have to be true before either becomes worth core-team prioritization?**
1. A built Meteor bundle boots and serves HTTP on the alternative runtime (spike proves this)
2. The MongoDB driver runs without memory leaks on that runtime (Bun team fixes #12117, or Deno proves stable)
3. runtime.js Module patching either works or has been refactored to be runtime-agnostic
4. At least one real Meteor app (with accounts, methods, publications) passes a 24-hour soak test
5. Community demand exists (forum thread, GitHub discussion with meaningful support)

### Bottom line

**Run the spikes in this order: Spike 0 → 1 → 2 → 3 → 5.** This takes one weekend and gives you 90% of the signal. Spike 4 (vm replacement) is the most valuable refactor regardless of outcome. The refactors R1-R4 are worth PRing to Meteor even if alternative runtime support never ships — they make boot.js cleaner and more portable.
